# Client-Server-exchange: переход на CMake, SOLID/DRY/KISS, GoogleTest

Дата: 2026-11-17. Ветка: `cmake-refactor` (от `boost-1.92`).

## 1. Зачем

Текущий проект — тестовое задание (ТЗ в `TestTask.docx`), но собирается только старым
`.sln`, который ссылается на отсутствующий `spdlog-1.x\spdlog.vcxproj`, содержит
захардкоженные пути к Boost, глобальные синглтоны через макросы (`SERVER`, `CLIENT`,
`log_write`) и не имеет ни одной точки, пригодной для автотеста. Цель: сборка через CMake,
код, соответствующий ТЗ и пригодный к защите (SOLID, DRY, KISS, GoF-паттерны там, где они
оправданы), покрытие GoogleTest.

## 2. Цели / не-цели

Цели:
- CMake-сборка без `.sln`: `cse_core` (статическая библиотека), `cse_server`, `cse_client`, `cse_tests`.
- Поведение строго по ТЗ (см. §4), включая то, что текущий код делает не по ТЗ.
- Логика тестируется без запуска процессов: юнит-тесты ядра + интеграционные на loopback.
- Никаких синглтонов, мешающих тестам: композиция в `main`.
- Boost там, где он уместен (asio, lockfree/synchronized_value вместо самодельной очереди).

Не-цели:
- Кроссплатформенность. Windows-only (`conio.h`, `wincolor` sink) остаётся, но прячется за интерфейсом.
- Изменение протокола обмена (4 байта запрос, 8 байт ответ, порт 64000).
- Сохранение обратной совместимости с текущим форматом `.dmp` (см. §4.3 — формат меняется по ТЗ).
- Удаление старых MSBuild-файлов (`*.sln`, `*.vcxproj`, `spdlog.vcxproj`) — только по отдельной команде.

Анти-цели (считать провалом, даже если «работает»):
- Абстракции ради абстракций (интерфейс на каждый класс, фабрика фабрик).
- Опрос в цикле (`sleep_for(1ms)`) вместо событий.
- Хранение глобального состояния, из-за которого тест не может создать два независимых сервера.
- Тесты, требующие ручного запуска сервера снаружи.

## 3. Рассмотренные подходы

1. **Только CMake, код как есть.** Дёшево, но тестировать нечего: логика в глобальных
   синглтонах, соединение и хранилище сшиты, нет границ. Не даёт требования задания.
2. **Слои + интерфейсы по швам (выбран).** Ядро без сокетов и без консоли: репозиторий
   чисел, расчёт среднего, кодек протокола, писатель дампа. asio-слой (`session`, `server`,
   `client`) — тонкий, поверх ядра. Композиция в `main`, инъекция зависимостей по
   конструктору. Интерфейсы только там, где тест реально подменяет реализацию.
3. **Гексагональная архитектура с портами на всё** (транспорт, хранилище, логгер, время,
   генератор, дамп — каждый порт + адаптер). Максимально «SOLID-образно», но +40% файлов
   и слои трансляции типов, которые ТЗ не окупает. Отклонено как противоречащее KISS.

Выбран вариант 2: он даёт тестируемость и DIP, не превращая 700 строк в 3000.

## 4. Поведение (по ТЗ)

### 4.1 Протокол
Клиент → сервер: `uint32` (одно число, 0..1023). Сервер → клиент: `uint64`
(среднее арифметическое квадратов). Порядок байт — как сейчас, host order, `memcpy`
фиксированной ширины. Кодек вынесен в `cse::protocol` и проверяет размер буфера.

### 4.2 Хранилище — глобальное
ТЗ: «сервер получает эти числа и сохраняет их в некий контейнер… среднее арифметическое
от квадратов **всех сохранённых чисел**». Текущий код хранит **множество на каждое
соединение** (`salg::storage_numbers::storage` — `unordered_map<uint32_t, set>`), то есть
каждый клиент видит только свои числа. Приводим к ТЗ: один контейнер на сервер,
`std::set<uint32_t>` (не `unordered_set` — детерминированный порядок нужен для дампа и
тестов). Среднее считается по всем уникальным числам, включая только что полученное.
Сумма квадратов поддерживается инкрементально (`uint64`), чтобы ответ был O(1) —
`1024 * 1023² ≈ 1.07e9`, переполнения нет.

### 4.3 Дамп
ТЗ: «каждые N секунд сервер сохраняет в файл все числа из контейнера; файл бинарный».
Текущий код пишет **текст** (`ofs << num`) и **квадраты**. Приводим к ТЗ:
- один файл `numbers.dmp` в рабочем каталоге, содержимое — `uint32` каждого числа подряд,
  `N * 4` байт, порядок возрастания;
- запись через отдельный поток (не поток обмена с клиентами), интервал `N` — параметр
  конфигурации (`--dump-interval`, по умолчанию 5 с);
- файл перезаписывается при каждом дампе (атомарно: пишем `numbers.dmp.tmp` → `rename`).

### 4.4 Остановка и логи
ESC в консоли — штатная остановка сервера и каждого клиента (как сейчас). Закрытие консоли
штатной остановкой не считается — поведение не меняем. Логи: консоль + файл
(`server.log`, `client.log`) через spdlog, формат строки как сейчас.

## 5. Структура кода

```
CMakeLists.txt                  корень: C++20, /W4 /permissive- /utf-8, опции
cmake/CompilerWarnings.cmake    флаги MSVC/GCC
Core/                           cse_core (static, без консоли и без main)
  include/cse/
    logger.h            ILogger + SpdlogLogger (Adapter)
    numbers.h           numbers_repository (SRP: только данные) + locked_repository (Proxy)
    mean_of_squares.h   free function + cached sum
    protocol.h          request/response codec, размеры, bounds check
    random_source.h     IRandomSource + MtRandomSource (Strategy)
    dump_writer.h       поток дампа: pull-модель, бинарная запись, stop
    stop_source.h       IStopSource + ManualStopSource (для тестов)
    session.h           asio-сессия: read 4 → add → mean → write 8 → read …
    server.h            tcp_server + server_app (Facade)
    client.h            client_app: connect с 3 попытками, цикл обмена
    options.h           разбор argv (host/port/интервал), значения по умолчанию
Server/main.cpp         композиция: логгер → сервер → ESC → stop
Client/main.cpp         композиция: логгер → клиент → ESC → stop
Tests/
  CMakeLists.txt        FetchContent(googletest), CTest
  *_test.cpp            10 наборов (см. §7)
```

Зависимости: `cse_core` ← `cse_server`, `cse_core` ← `cse_client`, `cse_core` ← `cse_tests`.
`Core` не знает про `main`-и, `main`-ы не знают друг про друга.

Диаграмма (упрощённо):

```
server_app ──uses──> tcp_server ──accepts──> session ──uses──> numbers_repository (Proxy)
    │                    │                      │                 └─> numbers_store (данные)
    │                    │                      └──uses──> protocol::encode_response
    │                    └──shares──> io_context  (инжектится, не синглтон)
    └──owns──> dump_writer ──reads snapshot──> numbers_repository
                    └──uses──> ILogger

client_app ──owns──> client ──uses──> io_context, IRandomSource, protocol::decode_response
```

## 6. Паттерны (только те, что окупаются)

| Паттерн | Где | Зачем |
|---|---|---|
| Facade | `server_app`, `client_app` | `main` не знает про asio/потоки/таймеры: один `start()/stop()` |
| Adapter | `SpdlogLogger` → `ILogger`; `MtRandomSource` → `IRandomSource` | ядро не зависит от spdlog и от `std::random_device` |
| Strategy | `IRandomSource`, `ILogger` | в тестах — детерминированный генератор и записывающий логгер |
| Proxy | `locked_repository` над `numbers_store` | SRP: данные отдельно, синхронизация отдельно; тест на «голом» хранилище без потоков |
| Factory | `session_factory` (создание сессий в acceptor) | acceptor не собирает сессию руками, тест подставляет фабрику |
| Observer | `IStopSource` + список обработчиков остановки | ESC/сигнал → остановка компонентов без синглтона |
| Iterator | `repository.snapshot()` (вектор) | дамп и тесты итерируют копию, а не живой контейнер под локом |
| Singleton | **удалён** | заменён композицией в `main`; макросы `SERVER`/`CLIENT`/`log_write` исчезают |

Отклонены как неокупаемые: Command (остановка — это `stop()` у Facade), State (асинхронный
read→write цикл сам является состоянием), Builder (три поля конфигурации), Memento.

## 7. План проверки (ID для `-qa.md`)

Юнит (`cse_tests`):
- **T1** `numbers_store`: дубликаты игнорируются, размер и сумма квадратов верны.
- **T2** `mean_of_squares`: пусто → нет значения; 0; 1023; 1..1023 (границы и переполнение).
- **T3** `locked_repository` (Proxy): 8 потоков × 1000 добавлений → размер == число
  уникальных, сумма не теряется.
- **T4** `protocol`: encode/decode запроса (4 байта) и ответа (8 байт), roundtrip,
  отказ при неверном размере буфера.
- **T5** `dump_writer`: файл `N*4` байт, содержимое == snapshot по возрастанию, повторный
  дамп перезаписывает файл, `stop()` завершает поток (нет зависимости от времени сна).
- **T6** `random_source`: значения в 0..1023 для сида 42 детерминированы.
- **T7** `options`: значения по умолчанию (порт 64000, интервал 5), разбор `--port`,
  `--dump-interval`, некорректный ввод → ошибка.
- **T8** `logger`: `ILogger` пишет в файл (временный каталог), уровень фильтруется.

Интеграционные (реальные сокеты на `127.0.0.1:0`):
- **T9** сервер + один клиент: три числа → ответ = среднее квадратов уникальных;
  повтор одного числа среднее не меняет (глобальное хранилище).
- **T10** сервер + два клиента: числа второго клиента видны первому (проверка глобальности).
- **T11** штатная остановка: `server.stop()` при подключённом клиенте завершается < 2 с,
  клиент получает признак завершения, процессов-зомби нет.
- **T12** клиент без сервера: 3 попытки подключения → выход с ошибкой, не вечный цикл.

Сквозная ручная проверка (вне CTest): 1 сервер + 10 клиентов, 10–20 минут — как требует
ТЗ; смотрим `numbers.dmp`, `server.log`, отсутствие роста памяти.

## 8. Сборка

```
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -DBOOST_ROOT=D:/libs/boost_1_92_0
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```
Boost — cache-переменная `BOOST_ROOT` (дефолт `D:/libs/boost_1_92_0`), только
заголовки + `Boost::headers` при наличии конфига. spdlog — `add_subdirectory(spdlog-1.x)`
(vendored, уже в репозитории). GoogleTest — `FetchContent` (URL-архив 1.15.2), с
возможностью `-DCSE_USE_SYSTEM_GTEST=ON`.

## 9. Риски и открытые места

- **Поведение меняется по ТЗ**: глобальное хранилище вместо per-connection, бинарный дамп
  целых чисел вместо текста квадратов, `numbers.dmp` вместо `N.dmp`. Это осознанно; старый
  клиент совместим (протокол не менялся), старый дамп — нет.
- Boost 1.92 берётся из локального пути; на другой машине нужен `-DBOOST_ROOT`.
- Stryker-стиль проверки гонок недоступен (нет ThreadSanitizer на MSVC): тест T3 ловит
  потерю данных, но не тонкие гонки чтения.
- Старые MSBuild-проекты остаются в репозитории и не поддерживаются; удаление — по команде.
